## Issue 1 — Retest-queue cascade (looks like a multi-hour/multi-day "hang")

**Sessions hit:** `ses_02365785dffep2DVqfsTTN8JKo` (v2secure.vn, ran ~30h), `ses_02509594effegpSV57VuDEA1xU` (192.168.5.148:3000 / juice shop, ran ~70.6h — "1 or 2 days")

**Root cause (two-part):**
1. Pre-existing, already-committed bug in `checkTriggers()` — `packages/cyberstrike/src/session/web/web-retest.ts:240-296`. It accepted a `relatedObjectIDs` param but never used it to filter; it fanned every new-object-value discovery out to up to 20 *unrelated* requests in the session.
2. Uncommitted new code (one of the 9 pending changes, see below) — `enqueueRetests()` in `server/routes/session.ts` — auto-drains the retest queue after every ingest and recursively re-invokes itself on each retest's completion. This turned the previously-inert over-fanned queue into an actually-executed, unbounded cascade.

Confirmed via `web_retest_queue` table in `~/.local/share/cyberstrike/cyberstrike.db`: N discoveries × ~18-20 fan-out each, all eventually `status='completed'` — it wasn't a true infinite hang, just a wildly inflated backlog that took days to grind through, then correctly went idle (which is why it *looked* frozen).

**Fix applied (source only):** `web-retest.ts` — added `relevantRequestIDs()` helper using existing provenance columns (`WebObjectTable.created_request_id` / `updated_request_ids`, `WebFunctionTable.objects`) and filtered the candidate `requests` list by it whenever `relatedObjectIDs` is provided. Falls back to the original all-requests behavior when `relatedObjectIDs` is absent — important because `web-write-role.ts` calls `checkTriggers` *without* it on purpose (a new role should re-test broadly; RBAC can affect any endpoint).

**Not done (explicitly deferred by user):** capping recursion depth in `enqueueRetests` (session.ts) as a secondary safety net.

**Unrelated pre-existing issue noticed while typechecking:** `session.ts:337` — `CoverageNote.wideBlock(sessionID, req.origin)` — `req.origin` is `string | undefined`, function wants `string`. Inside the uncommitted `buildRetestPrompt`. Left alone, out of scope.

**Verification caveat:** the server was rebuilt once after this fix (for Issue 2, see below), and the currently-running binary's mtime (04:58) is after `web-retest.ts`'s mtime (04:39), so the fix *should* be included — but I could not confirm this conclusively via `strings` (minification strips/renames non-exported identifiers and comments, so absence of a string isn't proof of absence). **Recommend verifying behaviorally**: trigger a new `web_write_object_value` discovery in a live session and confirm the resulting `web_retest_queue` rows are scoped to only the endpoints touching that object, not ~20 unrelated ones.

## Issue 2 — "The model `Qwen/Qwen3.6-27B` does not exist" (404)

**Session:** `ses_02509594effegpSV57VuDEA1xU` (same session as above — this error is what finally killed its 70h cascade, at `2026-08-10T07:16:59 UTC`)

**Root cause:** not a CyberStrike bug — infra/config drift. The self-hosted vLLM backend (`https://124.197.18.226:8000`) was reconfigured: served model renamed from `Qwen/Qwen3.6-27B` to `v2cloud/security-model-ft`, and `max_model_len` doubled to 256000 (verified directly via authenticated `GET /v1/models`). CyberStrike's config still referenced the old id, so every request 404'd once the rename took effect.

**Fix applied:** `~/.config/cyberstrike/cyberstrike.jsonc`, provider `vllm` → `models`:
```jsonc
"v2cloud/security-model-ft": {
  "name": "Qwen 3.6-27B (v2cloud FT)",
  "limit": { "context": 256000, "output": 16000 }
}
```
(replaced the old `Qwen/Qwen3.6-27B` entry)

**Status: done and deployed.** Server was rebuilt and restarted; confirmed the new process (PID 1116977, started 04:58) is actively using `v2cloud/security-model-ft`. Config is loaded once per process and cached (`Instance.state()` in `project/instance.ts`), so any *future* config edits need another restart.

## Issue 3 — Permission "Accept" click has no effect, session looks stuck

**Session:** `ses_00ff1c0f4ffe1hWlWSMKatjlFg` (v2secure.vn, new run after the Issue 2 fix)

**Root cause chain (fully confirmed via bus/event log correlation):**
1. Permission asked at `09:21:31 UTC` (only one `type=permission.asked` bus event logged for this session).
2. Nobody answered within 10 minutes, so the 10-minute auto-reject timeout in `permission/next.ts:158-163` (itself one of the 9 uncommitted pending changes, added during the 2026-08-06 hang investigation — see `issue.md`) fired at `09:31:31 UTC`. It deletes the pending entry and rejects the tool call **directly**, bypassing `PermissionNext.reply()` entirely — so it **never publishes `Event.Replied`**. Confirmed: zero `type=permission.replied` events anywhere in the log, despite 14 reply POSTs later.
3. Frontend never received a resolution event, so its local store kept displaying the permission prompt as live — a "ghost" prompt that looks answerable but isn't.
4. The rejection also legitimately (by design) stopped the whole turn: `processor.ts:224-229` sets `blocked = shouldBreak` on any `PermissionNext.RejectedError` (`shouldBreak` defaults `true` unless config sets `experimental.continue_loop_on_deny`), and `processor.ts:430` returns `"stop"`. So the turn correctly ended at `09:31:31` — not a true infinite loop, just an unresumable stopped turn with a misleading UI telling the user nothing happened.
5. User returned at `09:34:21 UTC`, saw the stale prompt, clicked Accept — fired **14 identical POSTs** to `/session/.../permissions/per_ff020868d0016Y0uYITn6rNqEZ` over 15 seconds. Every one hit `if (!existing) return` in `reply()` (`next.ts:180`) as a silent no-op — server still returns `200 true` regardless, zero feedback that the click did nothing.

**Fix proposed, NOT yet applied:** make the timeout path in `permission/next.ts` also publish `Event.Replied` (or a distinct "expired" event), same as the manual reply path, so the frontend can dismiss the stale card and tell the user it timed out instead of leaving a dead-but-clickable prompt.

**Separate, bigger, undecided design question:** should a single permission rejection hard-stop the entire turn (current default), or should it be fed back to the model so it can adapt and continue (how Claude Code itself behaves — permission denial there is just context for the agent to reason about, not a kill switch)? Discussed, no decision made. Worth a deliberate call, not a quick patch — CyberStrike's unattended, hours-long autonomous engagements don't have the same "human is watching live" assumption Claude Code's interactive sessions do.
